# v1.1.0 阶段 U 设计冻结：发布级系统验收与候选发布

状态：2026-09-11 在阶段 T 人工核验通过后自动冻结。阶段 U 完成后只创建
`v1.1.0-rc.1`，不得合并 `main`，也不得创建正式 `v1.1.0` 标签；项目负责人将在最终人工
卡口决定批准、要求修订或终止发布。

## 1. 目标、基线和范围

U 阶段原则上不增加数值算法、离散公式或配置语义，只对已获批准的 P--T 集成结果执行发布级
复验、安装和打包。若验收中确实需要改变算法或数学定义，必须建立独立修复提交，同时补充
对应公式和重跑受影响阶段卡口；本阶段实际触发的 Case07 输出侧修复登记在第 7 节。

发布基线为本地 `release/v1.1.0` 的 T 非快进合并提交 `9d276b2`。U 分支固定为
`stage/v1.1.0-u`。用户维护的 `cases/manual/case06_2d_naca0012/` 明确不属于 v1.1.0 范围，
自动工具、打包清单、Git 暂存和验收均不得读取或改动该目录。Case07 Mach 5 圆柱必须进入
发布验收。

本机冻结工具链为 Windows、CMake 3.28.0、MinGW-w64 GCC 8.1.0 和 Intel MPI 2021.10；
严格实测 Release 串行及 MPI 1/2/4/8 rank。Linux GCC/Clang、OpenMPI 和 Debug Sanitizer
由 `.github/workflows/ci.yml` 的冻结作业覆盖。若候选形成时无法同步并取得远端作业结果，
报告必须标为“外部 CI 待执行”，不得伪报通过；是否允许在该条件下合并由最终人工卡口判断。

WCNS 自有代码尚未选择对外许可证。本候选只能是私有/内部发布；源码包必须包含
`LICENSE.md` 和 `THIRD_PARTY_NOTICES.md`，文档不得暗示自由再分发。

## 2. U0--U6 任务和提交边界

1. **U0 设计冻结**：冻结本文件、平台证据边界、矩阵阈值、产物内容和停止条件。
2. **U1 版本与文档**：把 CMake 项目版本更新为 1.1.0；更新 README、用户手册、运行速查、
   开发指南、完整配置、已知限制并新增 `release-notes-1.1.0.md`。所有新增键、默认行为、
   检查点迁移、性能口径和许可证状态必须可检索且相互一致。
3. **U2 发布包**：增加确定性通用源码打包入口。包只从 `HEAD` 已跟踪文件构造，写入
   `WCNS_SOURCE_REVISION`、逐文件 `PACKAGE_CONTENTS.sha256` 和归档 SHA-256 sidecar；同一
   提交连续打包字节一致，篡改或未提交 payload 必须拒绝。
4. **U3 洁净构建/安装**：从此前不存在的串行、MPI 构建目录执行 Release 配置、无增量编译、
   全量 CTest 和安装；再从解包后的空目录独立配置、构建、安装、运行及同/异 rank 重启。
5. **U4 发布矩阵**：执行本文件第 3 节数值、并行、输出、重启和失败矩阵；Case07 使用独立
   U 工作目录，不能覆盖已跟踪的 Q 阶段结果。
6. **U5 性能与证据聚合**：重复 T 固定性能协议，核对 P--T 候选/批准标签、非快进合并、
   机器可读阶段摘要和发布包哈希。
7. **U6 候选封版**：生成机器可读 U 摘要和人工验收报告，执行最终差异/Git 审计，创建
   不可移动的带注释标签 `v1.1.0-rc.1`，随后停止。

每项独立提交。普通试跑输出只留在忽略的 `build-u-*`/`dist/` 下，不提交生成物；正式报告只
记录可复现命令、阈值、摘要、哈希和来源提交。冻结矩阵失败不得靠事后放宽阈值关闭。

## 3. 冻结发布矩阵

### 3.1 构建、规格和基础回归

- Windows 串行与 Intel MPI Release 均从空目录构建，编译输出不得含未解释 warning；
- 串行 CTest 60/60、MPI CTest 108/108、`tools/verify_algorithm_spec.py` 6/6 全部通过；
- MPI 测试及发布算例实际覆盖 1/2/4/8 rank，不能用多个串行进程代替；
- CI 配置静态审计确认 Linux GCC/Clang、OpenMPI、ASan/UBSan 作业仍引用当前构建/测试入口；
  远端结果只在真实取得后记为通过。

### 3.3 性能

重复 `tools/run_stage_t_performance.py` 的同机器、同绑核、High priority、一次预热、五次正式
样本协议。二维等熵涡和三维黏性中位数相对 P 基线加速均须 `>=1.5x`，Case07 20 步短算不得
回退；每组 CV `<=5%`。allocation probe 相对 S 基线减少 `>=90%` 且第二次 residual 不回升；
detailed 关闭时开销 `<=2%`；4-rank 强扩展效率 `>=70%` 且每 rank 至少 15,552 单元。弱扩展
只记录效率和通信分解，不新增掩盖单机内存带宽的阈值。

## 4. 源码包、安装树和复现卡口

源码包顶层名固定为 `wcns-1.1.0-source-<12位提交>`，至少包含构建文件、`include/`、`src/`、
发布工具、配置模板、可运行示例、文档、第三方归档和许可通知；不得包含 `.git`、构建目录、
运行输出或未跟踪用户目录。归档时间、所有者、权限和文件次序由来源提交确定。

自动验收必须：

1. 连续生成两份归档并证明 SHA-256 完全相同；
2. 校验 sidecar、包内逐文件 manifest，确认无额外或缺失 payload；
3. 解包至空目录，在没有 `.git` 的条件下配置并确认 manifest 中
   `program_version=1.1.0`、`git_commit=<WCNS_SOURCE_REVISION>`；
4. 完成 Release 构建、安装、网格生成、正式求解 dry-run、短程求解、检查点生成及重启；
5. 审计安装树含二进制、模板、示例、用户文档、发布说明、许可证和第三方通知。

## 7. 验收中发现的独立修复

Case07 首次完整运行在激波到达壁面的 `t=0.5` 输出事件暴露两个只属于诊断链的问题：Mach 5
Euler 配置请求了载荷不需要的 `T_w,mu_w`，且边界写出器无条件计算未请求的温度/输运量；随后
高阶内部壁压迹的非正输出侧超调会反向终止一个已经通过求解器正性检查的接受状态。

- `a571ee4` 将两个 Mach 5 配置收紧为压力、`Cp`、压力/总牵引，并使无粘写出只计算实际请求
  的热学量；边界测试改按列名验证，避免把列位置固化为隐式接口。
- `eaa6857` 为无粘诊断压力/温度迹增加《算法补充》11.4.4 的分段保护：高阶迹非法时退回最近
  内部真实单元正值。该值只进入输出，不回写状态，不改变通量、残差、时间步或重启签名。
- `2096a17`、`fe48922` 修复 U 卡口对 manifest 重复 `file=` 清单及 Q 阶段“最差尝试候选态”
  的解析语义；非正候选必须有 troubled-cell 与重算/重试证据，最终接受态仍必须严格为正。

修复后定向边界/Sutherland 测试和算法规格检查通过；Case07 以相同 4-rank、`t=8` 冻结参数
重新从头执行，未放宽物理时长、CFL、恢复上限或验收阈值。
